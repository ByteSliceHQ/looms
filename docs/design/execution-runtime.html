Composable Event-Sourced Execution Runtime

A durable execution kernel for agentic software.

Runs provide durability. Executions provide computation. Events provide truth. Reducers provide behavior. Effects cross into reality. Runtime Modules make the entire system open for composition.

Run = durability boundary Execution = computation unit Events = facts Effects = intent Modules = composition
Sections marked Source foundation summarize the supplied State Machine Overview transcript. Sections marked Design extension incorporate the newer pluggability and ecosystem ideas developed afterward.
01
Source foundation

The Runtime Thesis

The architecture is an event-sourced execution runtime. A Run is the durability boundary. Every agent, DAG, node, child execution, signal, and observable result participates in one durable event universe for that Run.

An Execution is the universal unit of computation. Each Execution owns a state machine. Events are immutable facts. Pure Reducers reconstruct state and request Effects. Effects cross into nondeterministic reality and eventually return observable results as new Events.

Event→Reducer→State + Effects→World→Event
Core invariant: the only way logical runtime state changes is by processing an Event.

The extension explored in this document is that the runtime should know almost nothing about “agents” themselves. If Events, Execution kinds, Reducers, Effects, projections, and adapters are open extension points, the system becomes a composable runtime substrate rather than a fixed agent framework.

From Agent Framework to Execution Platform

The important shift is from a framework that exposes a hard-coded Agent class to a runtime whose application model is expressed through a small set of universal primitives:

Application packages
↓
Events · Execution kinds · Reducers · Effects · Projections
↓
Runtime protocol
↓
Durability · scheduling · replay · waiting · causality · recovery

“Agent,” “DAG,” “browser worker,” “approval workflow,” “LLM turn,” or “payment operation” can all become higher-level packages built on top of the same execution semantics.

“

Not an agent runtime with DAG support, but a durable event/effect machine where agents and DAGs are merely kinds of executions.

Source foundation

Core Vocabulary

Run

The event-stream and durability boundary for one logical operation. One canonical durable stream contains the Events produced within that Run.

Execution

The universal runtime unit of computation. It belongs to a Run, may have a parent, has a kind, and owns a state machine plus execution state.

Execution Kind

A behavioral specialization of Execution such as agent, DAG, node, LLM turn, approval, or a user-defined kind.

State Machine

The behavioral model owned by an Execution. Different kinds have different state spaces and transition rules.

State

Durable logical state reconstructed from history. State is a projection, not canonical truth.

Event

An immutable fact appended to the Run stream. It describes something that already happened.

Signal

An externally originated Event used to steer, wake, pause, cancel, resume, approve, or add context.

Reducer

Pure logic mapping current State + Event into next State + zero or more Effects.

Effect

A requested consequence: an instruction to the runtime to cause something in the world.

Projection

A derived view over the canonical Run stream: runtime state, UI state, analytics, indexes, debugger state, and more.

Execution Tree

The parent/child hierarchy answering “who belongs to or invoked whom?”

Causation Graph

The event relationship answering “what caused this to happen?”

Replay

Reconstructing State by reducing previously recorded Events without blindly repeating Effects.

Snapshot

A persisted projection checkpoint that accelerates reconstruction of long histories.

Wait

A durable condition where an Execution consumes no worker until a matching Event arrives.

Runtime Module

A composable package that contributes Events, Execution kinds, Reducers, Effects, projections, handlers, or adapters.

Formal Model

A Run is the canonical durable log:

R = (r, L)
L = ⟨e₁, e₂, …, eₙ⟩

The Executions participating in a Run form a universe with a parent relation:

XR = { x | x is an Execution belonging to Run R }
parent : XR ⇀ XR

Each execution kind k defines a transition function:

δk : Sk × E → Sk × F*
(st+1x, Φtx) = δk(stx, et)

Projections reconstruct derived state from the event history:

P(L0…n) = fold(reduce, S₀, ⟨e₁…eₙ⟩)

Causal ordering is distinct from execution hierarchy:

eᵢ ≺c eⱼ iff causationId(eⱼ) = id(eᵢ)

The Event / Effect Boundary

EVENT

Immutable fact

Something already happened.

  • LLMResponseReceived
  • NodeCompleted
  • ExecutionCancelled
  • ApprovalGranted
EFFECT

Requested consequence

Something the runtime should cause.

  • CallLLM
  • SpawnExecution
  • SendWebhook
  • WaitForEvent
Event → Reducer → State + Effects
Effect → World → Event

This boundary is the key to durable replay. Replaying history recomputes State; it does not blindly repeat nondeterministic work.

Child Executions, Signals, and Durable Waiting

Child execution

Parent reducer → SpawnExecution(B) → runtime → ExecutionStarted(B)

The parent moves into a durable waiting state rather than blocking a call stack.

WAITING_FOR_CHILD + ChildCompleted(B) → resumed parent

Signals

A Signal is an externally originated Event injected into the same durable stream. It uses the same reducer machinery as internal Events.

Source foundation

Durability, Replay, and Ordering

The Run stream is canonical. Runtime state, browser state, analytics, debugger state, and indexes are projections over the same history.

Replay

Re-run pure reducers over recorded Events.

Recovery

Inspect durable facts around incomplete Effects and apply an explicit retry/resume/fail policy.

Snapshot

Resume reconstruction from a checkpoint rather than event zero.

Ordering

Strict order where one Execution needs determinism; concurrency where branches are unrelated.

currentState = snapshot(n) + reduce(events[n+1 … N])

Design extension

A Tiny Runtime Kernel

To become truly pluggable, the core library should know as little domain vocabulary as possible.

Runtime Kernel Run identity Execution identity + hierarchy event ordering + causation reduction effect dispatch waiting / waking snapshots / replay failure + cancellation semantics
AgentsDAGsLLM TurnsApprovalsBrowserPaymentsYour Module

The kernel should not fundamentally know what a “research agent,” “DAG node,” “tool call,” or “OpenAI message” is. Those concepts should arrive through modules.

10
Design extension

RuntimeModule: The Primary Extension Boundary

A coherent extension should be packaged as a Runtime Module. A module can contribute any combination of protocol-level capabilities. 

export const agents = defineRuntimeModule({
  namespace: "agent",

  events: {
    turnStarted: AgentTurnStarted,
    llmCompleted: LLMCompleted,
    toolRequested: ToolRequested,
    completed: AgentCompleted,
  },

  executions: {
    agent: AgentExecution,
  },

  effects: {
    callLLM: CallLLM,
    executeTool: ExecuteTool,
  },

  projections: {
    agentState: AgentStateProjection,
    conversation: ConversationProjection,
  },
})

A DAG package can independently contribute its own Event catalog, execution kinds, reducers, Effects, and projections. The runtime composes the modules into one execution universe.

Design extension

Bring Your Own Event Catalog

The Event vocabulary should be open-world. The core runtime should not require applications to extend one gigantic central union by hand. 

const payments = defineEventCatalog("payments", {
  requested: event({
    amount: number(),
  }),

  authorized: event({
    transactionId: string(),
  }),

  declined: event({
    reason: string(),
  }),
})

const runtime = createRuntime({
  catalogs: [
    coreEvents,
    agentEvents,
    payments,
    myCompanyEvents,
  ],
})

type Events = EventsOf<typeof runtime>
Type-system goal: module composition should infer the aggregate event universe automatically. Application authors should not manually maintain giant discriminated unions.
12
Design extension

Execution Kinds Should Be Open

The original architecture started with agents, DAGs, and nodes as Execution variants. A composable runtime should go one step more generic: 

interface Execution {
  id: ExecutionId
  runId: RunId
  parentId?: ExecutionId
  kind: string
}

Installed modules register the semantics of kind. That enables:

agentdagnodellm-turnbrowser-sessionhuman-approvalpaymentcustom

An Execution kind owns its state model and behavior, while the runtime owns durability and scheduling semantics.

13
Design extension

Two Different Reducer Contracts

“Bring your own reducer” is powerful, but the framework should distinguish behavioral reducers from observational projections.

EXECUTION REDUCER

Changes runtime behavior

reduce(state, event) => {
  state,
  effects,
}

Part of the execution semantics. It may request Effects.

PROJECTION REDUCER

Derives a view

project(state, event) =>
  state

Pure observation. It never causes Effects.

This distinction lets the same durable history drive runtime state, UI state, analytics, token usage, debugger timelines, billing, and custom customer views without confusing those views with execution semantics.

  initialState: { inputTokens: 0, outputTokens: 0 },

  reduce(state, event) {
    if (event.type !== "llm.completed") return state

15
Design extension

Effects and Handlers Should Be Pluggable

Third-party packages should be able to introduce Effects that the kernel has never heard of. 

defineEffect({
  type: "stripe.charge",

  async execute(effect, ctx) {
    const charge = await stripe.charges.create(...)

    return ctx.emit({
      type: "stripe.charge.completed",
      chargeId: charge.id,
    })
  },
})
custom Event → custom Reducer → custom Effect → handler → custom Event

The runtime contributes durability, idempotency hooks, cancellation, tracing, causation, waiting, and recovery semantics around that operation.

Source + extension

A Small Effect Instruction Set

The source conversation already converged toward four possible primitive Effect families. In a pluggable runtime, these become especially interesting as a kind of execution instruction set:

Invokecause external computation
Spawncreate another Execution
Emitcommunicate outward
Waitsuspend until an Event

Higher-level domain Effects can compile or lower into those primitives:

CallLLM(...)              → Invoke("openai.chat", ...)
DelegateToResearcher(...) → Spawn("research-agent", ...)
RequestApproval(...)      → Emit(...) + Wait(...)
SleepUntil(...)           → Wait("timer.fired")

This would let package authors invent high-level semantics without fracturing the underlying execution protocol.

17
Design extension

Keep a Small Standard Runtime Protocol

Not everything should be replaceable. Composability only works when modules share a small set of stable semantics.

The kernel probably needs a standardized protocol namespace for lifecycle and coordination facts such as: 

runtime.execution.started
runtime.execution.completed
runtime.execution.failed

runtime.signal.received
runtime.timer.fired
runtime.wait.registered
runtime.wait.satisfied

The exact catalog is still a design question, but the principle matters: modules can define unlimited domain vocabulary while relying on a small shared execution protocol.

Too little standardization: modules cannot interoperate.
Too much standardization: the runtime becomes another opinionated agent framework.
Target: a tiny rigid kernel with a huge open ecosystem.
18
Design extension

Type Inference Is Part of the Product

For a TypeScript runtime, composability is only attractive if installing modules also composes the types. 

const runtime = createRuntime({
  modules: [
    openai(),
    dag(),
    humanApproval(),
    stripe(),
    researchAgent(),
  ],
})

type Events = EventsOf<typeof runtime>
type Effects = EffectsOf<typeof runtime>
type Executions = ExecutionsOf<typeof runtime>
type Projections = ProjectionsOf<typeof runtime>

The runtime should infer event/effect discriminated unions, execution kinds, effect handlers, and projection handles from the module graph. This is not just developer convenience—it is what makes an open ecosystem feel coherent instead of dynamically glued together.

“

User code describes computation; the runtime controls execution.

React did not win because it was a library for buttons. It offered a small compositional model and separated application semantics from rendering infrastructure. The analogous opportunity here is a small compositional model for durable agentic computation.

22
Design extension

Where the React Analogy Breaks

The comparison should not hide the hard distributed-systems problems.

Durability

Executions may live for months and survive process failure.

Concurrency

Independent branches can race while same-target Events need deterministic order.

Nondeterminism

LLMs and external services cannot simply be replayed like pure functions.

Side effects

Exactly-once business semantics often require idempotency and reconciliation.

So “React for agentic harnesses” is best treated as an internal product-design north star: small core, declarative user model, huge composable ecosystem.

23
Design extension

Module Composition Rules

A plugin ecosystem needs deterministic composition semantics. The runtime should make these rules explicit early:

  • Every module has a stable namespace and version.
  • Event and Effect type names are globally unambiguous after namespacing.
  • Execution kinds may only have one owning behavioral reducer unless explicit composition is supported.
  • Projection reducers may freely observe Events from other modules.
  • Effect handlers must declare which Effect types they implement.
  • Module dependencies are explicit rather than inferred from runtime failures.
  • Protocol compatibility is versioned independently from package versions.
  • Event schemas are durable contracts and cannot be silently reinterpreted after persistence.
  • Module initialization must not mutate historical semantics.

  TEffects,

  namespace: TNamespace
  protocolVersion: string

  events?: EventCatalog<TEvents>

  projections?: ProjectionRegistry<TProjections>

The interesting library-design challenge is making createRuntime() merge those module-level types into one strongly typed runtime without forcing package authors to manually coordinate generic parameters.

Source foundation

Processing Loop

  1. Receive or observe a new Event for a Run, including externally originated Signals.
  2. Append or accept it according to the Run stream’s ordering guarantees.
  3. Resolve the target Execution and its registered execution kind.
  4. Reduce the Event using the Execution’s pure behavioral reducer.
  5. Update durable/materialized projections as appropriate.
  6. Dispatch returned Effects to registered Effect handlers or primitive runtime instructions.
  7. Append observable Effect outcomes back to the same Run stream with causation metadata.
  8. Repeat until the Execution is terminal, durably waiting, or more Events arrive.
Replay mode: execute only Event → Reducer → State/Projection. Historical Effects are not dispatched.

Open Questions Worth Designing Next

Core protocol catalog

Which lifecycle Events must every module understand, and which should remain domain-defined?

Module composition semantics

How do namespaces, reducer ownership, handler conflicts, and dependencies resolve?

Event schema evolution

How are durable Events versioned without breaking replay?

LLM call: Effect or Execution?

An LLM turn may deserve its own child Execution for fine-grained durability and cancellation.

Effect lowering

Should high-level Effects compile to Invoke / Spawn / Emit / Wait, or may handlers execute them directly?

Projection portability

What subset of reducer logic can run identically in backend, LiveStore, SQLite, and analytics environments?

Module capabilities

Should modules declare required runtime features such as timers, leases, transactions, or streaming?

Security boundaries

How do third-party Effect handlers and modules get sandboxed, permissioned, and audited?

27
Design extension

Implementation Sequence

A pragmatic path to validate the architecture:

  1. Kernel first: Run, Event envelope, Execution identity, reducer contract, Effect dispatch, causation, ordering, replay.
  2. One built-in module: implement Agent as a module rather than as privileged runtime code.
  3. Second independent module: implement DAG using the same public extension API. If this requires kernel exceptions, the plugin boundary is wrong.
  4. Projection API: make the same projection run in memory and through a LiveStore adapter.
  5. Third-party-style module: build a Stripe or GitHub module without importing internal runtime packages.
  6. Type composition: make Events / Effects / Execution kinds infer from installed modules.
  7. Package protocol tests: create a conformance suite that any module can run.
Litmus test: if “Agent” and “DAG” can both be deleted from the kernel and reinstalled as ordinary packages, the architecture is genuinely composable.

Appendix: Competitor Landscape

The market already contains strong implementations of individual pieces of this architecture. The closest systems validate the model from different directions: event-log-first agent harnesses, durable workflow engines, actor systems, state-machine runtimes, and reactive projection layers.

System Closest overlap Where our model goes further / differs
Tardigrade Composable TypeScript agent harness built around an immutable event log, projections, transitions, and effects. It also explicitly uses a React-like composition analogy. Its conceptual center is still the agent actor/thread. Our proposed center is the universal Execution, with agents, DAGs, LLM turns, approvals, browser sessions, payments, and third-party runtimes all participating as equal execution kinds.
Stately / XState Agent 2.0 Pure state-machine transitions, actor-style mailboxes, durable event logs, replay, causation/correlation metadata, snapshots, and effect completion as events. Very close mechanically, but currently agent-machine-centric rather than a general open runtime protocol with arbitrary execution kinds, event catalogs, effect families, and projection hosts.
Temporal Durable executions, child workflows, signals, deterministic replay, timers, activities, retries, and crash recovery. Temporal owns the workflow-history event vocabulary. Our proposal elevates application Events, Reducers, Effects, and Projections into the public programming model and makes them extensible.
Restate Durable objects/workflows, single-writer semantics, signals, durable waiting, and event-driven wakeups. Closer to an execution substrate than an open event/reducer/projection programming model. It could plausibly host parts of this architecture rather than replace it.
Akka / Apache Pekko Persistence Event-sourced actors, command/event/state separation, pure event handlers, snapshots, and projections. A major conceptual ancestor, but persistence is organized around actors/entities rather than a Run-wide heterogeneous execution universe with a TypeScript-first module ecosystem.
LangGraph Durable agent orchestration, graph state, checkpoints, human interrupts, subgraphs, resume, replay, and time travel. Its center is graph + node + checkpoint state. Our center is the canonical event log plus arbitrary Execution kinds, reducers, effects, and portable projections.
Inngest Event-triggered durable functions, checkpointed steps, sleep, wait-for-event/signal, and resumable execution. Strong match for the Invoke/Wait runtime machinery, but not the broader event-sourced execution protocol and plugin model.
DBOS Durable TypeScript/Python/Go/Java workflows backed by ordinary application code and persistent recovery. Primarily durable function execution, not a public event/reducer/effect/projection composition model.
LiveStore Event-sourced reactive projections materialized into local/queryable state. Excellent fit for the projection layer, but not an execution runtime. In our model LiveStore is an adapter/host for portable projections.
Effect Typed effects, dependencies, structured concurrency, interruption, retries, schedules, and tracing in TypeScript. Likely an implementation substrate for effect handlers/runtime services, not the canonical durable execution semantics themselves.
Landscape takeaway: the whitespace is not “durable agents” or even “React-like agent composition” by itself. The stronger differentiation is a universal event-sourced execution protocol in which agents are only one pluggable execution kind.

Strategic differentiation

Appendix: Points of Differentiation

Execution, not Agent, is the primitive

The runtime does not privilege agents. Agents, DAGs, LLM turns, approvals, browser sessions, payments, and custom third-party execution kinds share one substrate.

One Run-wide execution universe

Nested heterogeneous work participates in one canonical Run event stream, while hierarchy and causation are represented separately in metadata.

Open event catalogs

Applications and packages can bring their own durable Event vocabularies without forking or extending a monolithic framework-owned union.

Pluggable behavioral reducers

Execution kinds own pure state-machine/reducer semantics that can be registered through ordinary modules rather than kernel-only code.

Portable projections

The same Event history can drive runtime state, LiveStore UI state, Postgres views, ClickHouse analytics, local SQLite, debugger timelines, and custom projections.

Pluggable Effects and handlers

Third-party packages can contribute domain Effects and handlers while the runtime provides durability, causation, cancellation, tracing, retry, and recovery semantics.

Small shared execution protocol

A tiny standardized lifecycle/coordination protocol creates interoperability while leaving domain vocabularies and high-level semantics open-ended.

Effect instruction set

Invoke, Spawn, Emit, and Wait may form a low-level execution algebra beneath higher-level package Effects.

Type composition as product surface

Installing modules should automatically compose Event, Effect, Execution, and Projection types so an open ecosystem still feels like one coherent TypeScript program.

Infrastructure independence

Modules describe computation; adapters provide streams, snapshots, projection stores, worker execution, and other infrastructure without leaking into domain semantics.

“

The north star is not “React for agents.” It is a small compositional model for durable computation where agents are just one thing the ecosystem can build.

Strategic framing

The strongest competitive position is the combination of:

React-style composition+ actor/state-machine semantics+ Temporal-style durability+ event-sourced projections

Packaged behind one small TypeScript protocol, that creates a plausible foundation for a broad ecosystem rather than another opinionated agent loop.
